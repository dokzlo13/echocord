## Implementation checkpoint

The assigned worktree and branch were verified before implementation. The worker changes only `crates/core/src/audio.rs` and this task record. Shared exports, manifests, lockfiles, and model types remain coordinator-owned. Task completion still requires coordinator integration and the native/live acceptance work below.

Implemented the agreed `enumerate_sources` / `start_capture` / `CaptureSession { input, control }` API. `CaptureControl` is cloneable and supports idempotent stop, output volume/mute, and the existing `model::Capture` snapshot. `LivePcm` implements Read, Seek, MediaSource, Send, and Sync; it is nonseekable with unknown length and accepts a position query only. Non-Windows capture calls return an explicit error. Consumers should use `RawAdapter::new(session.input, 48_000, 2)`.

Windows capture enumerates WASAPI recording endpoints and matches the explicitly supplied CPAL `DeviceId`; no default device, friendly-name lookup, playback loopback, or automatic input selection. Configuration requires a supported 48 kHz mono or stereo format, preferring stereo and then f32. Supported sample types are i8/i16/i32/i64, u8/u16/u32/u64, and f32/f64, converted directly on callback slices; mono is duplicated to stereo. Unsupported rates/layouts/formats return a visible start error. Callback failures become Missing/Error snapshots; a late error cannot replace stop or the first failure. Raw backend errors and device identifiers are not included in error messages.

Queue and reader policies are initial engineering bounds, not measured latency results:

- Fixed SPSC storage for 1,920 complete stereo frames (40 ms at 48 kHz), using rtrb. Overflow rejects whole incoming frames. The consumer alone removes queued frames, with bounded discard work.
- Frames older than 40 ms since callback exposure are discarded at handoff. Fragmented callback input retains the first sample's age and mute generation. One already-started 8-byte output frame is completed across fragmented byte reads to preserve valid f32/stereo alignment.
- Each read returns at most 240 frames / 1,920 bytes. A 5 ms clock budget applies to audio and synthesized silence, including repeated refills by Symphonia. The reader cannot accumulate unlimited credit when consumption pauses; waits check cancellation at intervals of at most 2 ms of requested sleep.
- Starvation remains valid input and returns paced silence. Only terminal stop returns EOF; capture failures return a terminal I/O error. Mute drains or invalidates queued audio, and callbacks meter input before output gain even while muted. Every mute transition invalidates older frames, including mute/unmute with no intervening read.
- Callback code performs conversion, bounded queue operations, and atomic telemetry only: no locks, logging, network/UI calls, or dynamic sample allocation. Reader Sync uses a mutex wrapper around the non-Sync consumer, accessed exclusively via `get_mut`; sample transfer never locks. Stream destruction occurs outside callbacks.

- `cargo xwin test --locked -j2 --target x86_64-pc-windows-msvc --target-dir target --no-run -p echocord-core`: Windows unit binaries compiled.
- Executing the cross-built core unit binary on Windows with `audio::tests:: --nocapture`: 25 audio tests passed. These tests use synthetic PCM and never enumerate/open a capture endpoint or connect to Discord.
- The Windows-only reader test runs the actual Songbird RawAdapter, format probe, RawReader, and registered Symphonia PCM decoder for 100 packets: silence then stereo input, exact 960-frame packet durations/timestamps, decoded left/right sample checks, and clock/read-ahead bounds. The portable test exercises actual Symphonia MediaSourceStream refill growth and ring wraparound.

Portable tests cover byte and callback fragmentation, short reads, silence/resume, cancellation during pacing waits, terminal stop/failure, stale age, overflow/alignment, mute draining/generations, gain with pre-volume meters, invalid float samples, saturating telemetry, and both faster/slower producer pacing. Synthetic deterministic clocks test timing logic; they do not measure the Windows scheduler or an audio endpoint.

References inspected: [CPAL stable DeviceId](https://docs.rs/cpal/0.18.2/cpal/struct.DeviceId.html), [rtrb consumer thread guarantees](https://docs.rs/rtrb/0.4.0/rtrb/struct.Consumer.html), and the pinned local source for Songbird 0.6.0 and Symphonia 0.5.5 reader/decoder behavior.
