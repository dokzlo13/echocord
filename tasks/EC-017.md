## Architecture review checkpoint

The coordinator and independent reviewer accepted a bounded source-contract extension: a recording/application discriminator, opaque application IDs containing PID plus process creation time, and a separate local source-discovery status/refresh command. Discord REST discovery must not own or erase the local source list. Refresh changes the catalog, not the selected route; missing confirmed items retain their label and become unavailable. Application identity is revalidated before startup and held through capture; an exited application is terminal and requires explicit reselection. Persisted application IDs are cleared on a new app launch; recording preferences remain compatible.

Window discovery uses the window-owning process without walking upward into launchers or desktop processes. Captured scope is that process and its children; duplicate executable names need disambiguation. Browser tabs/windows may share that tree. Local source discovery works without bot configuration and can refresh while another route is active.

Pinned wrapper inspection independently identified unsafe handling of silent packet pointers and an unbounded activation wait in wasapi 0.25.0. Direct Windows bindings are the reviewed fallback for a small process-loopback adapter. The final activation lifetime, packet release, bounded shutdown and engine cleanup implementation still require code review and native evidence. No production capture result has yet been measured in this epoch.

Build one narrow Rust Windows process-tree capture experiment, with normal-user operation, source/build/tooling in WSL, and explicit synthetic test sources. Prefer the researched WASAPI wrapper after validating its pinned API. Capture only the included process tree; never silently widen to desktop/exclusion capture. Keep PCM within the engine; use bounded buffers, correct silence/packet flags, and observed cleanup. No credentials or Discord connection is needed to establish this boundary.

Acceptance evidence: selected/unselected signal isolation; browser process-tree scope; supported format and stereo behavior; silence/resume; source exit/restart and device changes; cancellation and queue age. ## Reviewed implementation seam (2026-10-10)

Coordinator and independent review accepted the minimal control contract: retain opaque `sourceId`, add descriptor `kind` (`recording`/`application`), `sourceDiscovery`, and `refresh-sources`. Local enumeration runs independently of bot setup/network discovery, can refresh while streaming, and never changes the selected route. Failed refresh preserves cached descriptors with an explicit error; a vanished selected descriptor remains visible but unavailable. Legacy descriptors default to recording. UI selection continues to require explicit draft/apply.

Application selection is one visible top-level window's owning process plus its descendants, deduplicated by root PID. It never ascends an arbitrary parent tree and never claims per-tab/window capture. IDs bind PID to process creation time, verified using a held process handle. Exited applications and restarted instances require explicit refresh/reselection; application IDs are cleared when restoring preferences. Recording endpoint IDs/preferences retain their existing meaning.

The pinned `wasapi` 0.25.0 source review found an unbounded activation wait and a packet reader that dereferences data before checking `SILENT`. Direct `windows` bindings are the reviewed fallback: capture objects stay on an MTA thread, activation/cancellation waits are bounded, late callbacks cannot start capture, included-tree mode is fixed, silent packets never dereference their data pointer, and PCM enters the existing bounded native reader. Actual unsafe/lifecycle code still requires independent review before integration.

Primary sources: [pinned wrapper activation/reader](https://github.com/HEnquist/wasapi-rs/blob/v0.25.0/src/api.rs), [Microsoft process-loopback sample](https://github.com/microsoft/Windows-classic-samples/tree/main/Samples/ApplicationLoopback), [activation lifecycle](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-activateaudiointerfaceasync), [packet lifetime/flags](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer), [process creation time](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes).
