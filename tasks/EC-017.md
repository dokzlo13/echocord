## Reviewed implementation seam (2026-10-10)

Coordinator and independent review accepted the minimal control contract: retain opaque `sourceId`, add descriptor `kind` (`recording`/`application`), `sourceDiscovery`, and `refresh-sources`. Local enumeration runs independently of bot setup/network discovery, can refresh while streaming, and never changes the selected route. Failed refresh preserves cached descriptors with an explicit error; a vanished selected descriptor remains visible but unavailable. Legacy descriptors default to recording. UI selection continues to require explicit draft/apply.

Application selection is one visible top-level window's owning process plus its descendants, deduplicated by root PID. It never ascends an arbitrary parent tree and never claims per-tab/window capture. IDs bind PID to process creation time, verified using a held process handle. Exited applications and restarted instances require explicit refresh/reselection; application IDs are cleared when restoring preferences. Recording endpoint IDs/preferences retain their existing meaning.

The pinned `wasapi` 0.25.0 source review found an unbounded activation wait and a packet reader that dereferences data before checking `SILENT`. Direct `windows` bindings are the reviewed fallback: capture objects stay on an MTA thread, activation/cancellation waits are bounded, late callbacks cannot start capture, included-tree mode is fixed, silent packets never dereference their data pointer, and PCM enters the existing bounded native reader. Actual unsafe/lifecycle code still requires independent review before integration.

Primary sources: [pinned wrapper activation/reader](https://github.com/HEnquist/wasapi-rs/blob/v0.25.0/src/api.rs), [Microsoft process-loopback sample](https://github.com/microsoft/Windows-classic-samples/tree/main/Samples/ApplicationLoopback), [activation lifecycle](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-activateaudiointerfaceasync), [packet lifetime/flags](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer), [process creation time](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes).

## Native adapter and measured evidence

The adapter uses pinned `windows`/`windows-core` 0.62.2 directly; no wrapper fork or driver is added. Process identity is canonical PID plus creation FILETIME. Query/synchronize handles remain held during activation and capture, so PID reuse cannot retarget a live session. Visible top-level window discovery omits Echocord's own tree and OS shell/desktop roots; capture start rejects shell/desktop roots too. Browser roots are the actual window owners, with no parent ascent. A selected hidden/tray application remains available while its exact identity is still running. Restarted applications require a new explicit selection; recording preferences still restore.

All capture COM interfaces live on one MTA thread. The callback owns immutable activation storage until completion; it only signals, including late completion after cancellation. Opening checks caller cancellation every 10 ms, activation waits at most three seconds, event waits at most 20 ms, and draining checks cancellation/process exit between packets. Stop waits at most 200 ms for capture-thread completion; a cleanup failure stays terminal across repeated stop calls and causes worker failure/exit instead of reopening another capture. The parent still owns forced process cleanup. The event handle outlives capture/client interfaces. Packet processing uses fixed stereo float format and bounded scratch, honors `SILENT` before dereferencing data, releases packets on early failures, and invalidates queued old input on discontinuity. Meter peaks are observed once per packet. Queue age starts when the native adapter exposes samples; it is not WASAPI backlog, complete pipeline delay, or listener latency.

Credential-free Windows measurements used only owned fixtures; no Discord session, owner source/settings changes, microphone capture, or endpoint mute occurred:

- Selected 48 kHz root stereo and a 44.1 kHz child were captured; an independent 2,233 Hz source was first positively captured by its own ID, then excluded from the selected tree. Selected-tree silence produced exact zero while the independent source kept rendering. Small live spectral projections at unrelated frequencies are the finite-window leakage floor, not evidence of captured unrelated playback.
- Silence/resume, native gain/mute zero output, same-root reopening, root exit, stale-ID rejection, and fresh-instance selection passed. Consumer pause kept the queue within 1,920 frames and discarded stale/overflow frames. Reopening the owned renderer on another playback endpoint preserved both root and child signals without changing Windows defaults.
- Original-source session mute removed the root signal from capture while its child's separate session remained captured. Quarter session volume reduced captured root amplitude to approximately one quarter. This path does not provide independent original-playback suppression. Physical speaker audibility and endpoint mute remain unmeasured; the UI must say original playback continues and offer no suppression control.
- A dedicated browser profile's actual visible root was returned by production discovery and captured two distinguishable tabs plus stereo, while excluding the independent renderer. Background autoplay was enabled only inside the disposable profile. The root/job was then observed exiting. This establishes process-tree/browser-wide scope, not tab/window isolation.
- Observed synthetic open/stop/cancel times were in the millisecond range; they are single-run observations, not latency budgets. A post-entry native cancellation handshake was exercised. Separate Windows unit tests held activation completion false while cancellation occurred, and verified late-callback storage ownership/agility and sticky cleanup failure.

The existing `capture-probe` supports `--application-suite` for owned tones and `--browser-suite FIREFOX_EXE OWNED_PROFILE FIRST_SYNTHETIC_URL SECOND_SYNTHETIC_URL` for an explicitly isolated browser fixture. Its browser owner uses a kill-on-close job and read-only held-handle membership checks, so a short-lived launcher cannot cause selection of an owner browser. Raw JSON, dedicated profile/pages, host paths and logs remain ignored. OS endpoint removal, sleep/resume, physical audibility, a live Discord app-capture session and five-hour stability remain later acceptance; Linux tests do not establish them.

Independent review and coordinator integration remain required. The coordinator owns final production UI/app build and global documentation reconciliation; this worker's native smoke addition also verifies local source discovery without configured credentials.
