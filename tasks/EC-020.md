## Accepted destination architecture checkpoint

The coordinator and independent EC-028 reviewer accepted a bounded continuation: up to four destination cards, comprising one Discord room and up to three explicitly selected Windows playback endpoints. Playback cards are added/restored idle and require explicit Play. No default-device fallback, automatic playback, driver installation, endpoint routing changes or implicit monitoring is introduced.

Each playback endpoint has its own tokenless disposable Windows worker and kill-on-close job. Only its inherited duplicate mapping handle can reach PCM; the controller remains unmapped. The device's native 48 kHz stereo output callback nonblockingly drains its independent current-cursor bus reader, applies precise atomic gain/mute, and observes completed callback output. No paced reader, sleeping, allocation, blocking pipe or controller mutex is allowed in the callback. Native format/open failures and slow/stalled consumers remain isolated to the selected output. Physical ownership remains reserved through opening/disconnect until observed exit; no endpoint is reused after unconfirmed cleanup.

Endpoint IDs are treated as opaque identities and revalidated in the render-device catalog at open. Duplicate endpoint selections are rejected. Supported format is explicitly 48 kHz stereo PCM; unsupported devices stay unavailable. Local buffer statistics describe shared-mix backlog, not total endpoint latency. Recording inputs can feed back when their paired cable output receives the mix; names/IDs alone cannot establish cable pairing, so the picker provides a concise routing warning. Application roots containing Echocord's own process tree must also be excluded.

Discord research distinguishes platform capability from this release's engineering bound. Discord documents guild-scoped voice state and explicitly permits multiple Gateway sessions with identical shard parameters. It does not make duplicate full gateway workers a demonstrated independent-teardown architecture. The pinned Songbird manager keys calls by guild, and its `join_gateway` API can return connection information for a separate driver. A later one-gateway plus disposable per-guild voice-driver design can support different-guild rooms while retaining process exit as local quiescence; same-guild simultaneous rooms require different bot identities. That lifecycle extension is deferred rather than shipping unverified duplicate gateways.

Primary sources inspected on the continuation date: [Discord Voice](https://docs.discord.com/developers/topics/voice-connections), [Discord Gateway sharding/session limits](https://docs.discord.com/developers/events/gateway#sharding), [Songbird 0.6.0 manager source](https://github.com/serenity-rs/songbird/blob/3f77b5fa6de3f7354fdd7ef0dfa861518d304cdd/src/manager.rs), [Songbird driver source](https://github.com/serenity-rs/songbird/blob/3f77b5fa6de3f7354fdd7ef0dfa861518d304cdd/src/driver/mod.rs), [CPAL 0.18.2 traits](https://github.com/RustAudio/cpal/blob/e1612d5d98152f8dc2a62e1b51ef7cbf4f7f26b7/src/traits.rs), [Windows endpoint identity](https://learn.microsoft.com/en-us/windows/win32/coreaudio/endpoint-id-strings), and [Windows rendering](https://learn.microsoft.com/en-us/windows/win32/coreaudio/rendering-a-stream). ## Implementation and validation checkpoint

Implemented one Discord plus up to three playback cards, independent device discovery, explicit Play/Stop, fractional gain/mute, per-output connection/session/telemetry, version-3 preference migration, idle restoration and all-output tray controls. Catalogs and playback controls work without Discord credentials and during Discord connection work. Exact endpoint IDs are revalidated at open, duplicate endpoints are rejected, and endpoint ownership remains reserved through stopping and unconfirmed cleanup. Removing an active card keeps cleanup visible until observed exit while persisting the removal intent immediately. Live endpoint replacement waits for the old worker's exit before starting the new endpoint. A per-output session generation fences status/meter observations and resets only that output's frontend history.

The native callback reads bounded atomic bus slots directly and emits stereo F32/I16/U16 at supported 48 kHz. Gain/mute use one atomic control word; mute transitions invalidate that reader's older backlog, including rapid mute/unmute between callbacks. Completed callback output owns its meter. Native callback observation is required before Playing, and startup/callback/cleanup deadlines do not depend on UI or pipe progress. Faulted output workers do not stop the shared producer, capture or other outputs. Application source discovery excludes Echocord's worker tree and ancestors; direct capture also rejects roots containing the current process without excluding unrelated sibling apps or introducing executable-name matching.

Checks passed at this checkpoint: 126 portable library tests plus nine probe tests; portable Clippy and generated-contract checks; Windows core all-target and application Clippy; and 132 Windows library tests. The shell smoke now requires both source and playback discovery to become Ready without issuing Play/Connect. No canonical owner application executable was rebuilt during this worker's validation.

A read-only native inventory identified an available 48 kHz stereo digital endpoint with no active sessions and no default roles. The coordinator authorized that exact API-issued endpoint for bounded tests; the probe rechecked those conditions before each start and made no endpoint/session-volume or routing changes. Native owned-worker process loopback verified stereo delivery, precise gain, mute/resume, a failed peer output leaving the healthy output intact, continued production after Stop, restart and observed process exits. The shared producer measured **47,958.7 frames/s**; the maximum observed native callback contained **1,056 stereo frames**. Portable callback tests separately exercise two independent readers, slow-reader overwrite containment, stale-producer silence and mute queue invalidation.

This proves one selected hardware playback path and independent native worker failure containment.
