## Bounded destination decision

Deliver at most four destinations: the existing single Discord destination plus up to three explicitly selected Windows playback endpoints. Each playback destination has an independent tokenless disposable job, shared-mix reader, device callback clock, gain/mute/meter and observed cleanup. Adding/restoring a playback card does not start output; Play is explicit. Initial supported format is 48 kHz stereo PCM with validated native sample formats. Endpoint identity is opaque and stable, duplicates are rejected, and missing/unsupported endpoints never fall back to the default.

Multiple cross-guild Discord rooms are feasible. Discord permits multiple gateway sessions; the reason for deferring parallel room workers is the application's current single-guild voice-state and disposal assumptions, not an API prohibition. The researched follow-on separates a shared gateway from independently disposable voice drivers, retaining reliable Cancel/Stop without disturbing other outputs. Native architecture/contract review must precede implementation of this increment.

Primary identity reference: [Microsoft endpoint ID strings](https://learn.microsoft.com/en-us/windows/win32/coreaudio/endpoint-id-strings). Friendly names can collide and IDs must not be parsed to infer input/output pairing. Sending a mix into a cable whose recording endpoint is itself captured can feed back; the output flow must explain the concrete routing condition without claiming unreliable automatic topology detection.
