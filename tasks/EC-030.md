# EC-030 Multiple Discord rooms

Active, native worker a1 on `agent/EC-030-a1` in `.worktrees/EC-030-a1`. Owner now requests planning and implementation of multiple room targets. Dependencies: shared mix and independently controlled output model, plus a reviewed gateway/voice-worker contract before implementation.

Research in EC-020 confirms different-guild calls are feasible. Discord permits multiple gateway sessions, but the current engine's single-guild event/disposal assumptions are not a validated multicall design. Explore one shared gateway owner using pinned Songbird's gateway-only join interface, with independently disposable per-guild voice drivers reading the same native mix. One bot still has one voice channel per guild; simultaneous same-guild rooms require separate identities and a separate credential/UI decision.

Preserve source and playback independence, backend-only credentials and voice connection secrets, bounded readers, per-output generation/gain/mute/telemetry, and observed worker exit as local quiescence. Define how gateway reconnects and stale voice-state/server events map to current room intent, how one guild cancels/leaves without restarting other calls, and how parent death/fatal gateway failure is contained. Do not silently replace the existing room or rejoin after removal/permission rejection.

Acceptance requires meaningful event-order/cancel/cleanup tests and a coordinated live test in separate guilds, including one output failing while another and local playback continue. No token/session data in frontend snapshots or diagnostics. Keep current explicit output UX; no routing matrix, driver or broad redesign is required. This record is a researched proposal, not an implemented capability.

## Reviewed one-bot architecture and public contract checkpoint

The owner confirmed different servers using the current bot. Keep four total destination cards and at most three playback cards; permit multiple Discord cards with at most one selected room per server. Same-server simultaneous rooms/multiple credentials are outside this increment. Source capture, playback workers and ordinary output controls retain their current behavior.

One parent-owned `--gateway-worker` owns the protected bot token, bounded REST work and one Serenity gateway. It receives no PCM handle. Each requested Discord room has a separately owned disposable `--voice-worker`, inheriting only its independent mix-reader handle and receiving bounded private voice connection data. The parent remains PCM-free and brokers private data only in backend IPC. Stop/Cancel, process exit confirmation, job kill fallback, output gains/mutes and per-room telemetry remain independently scoped.

The gateway uses a bounded map of Songbird `Call::from_config` instances with `Shard::Generic` and a gated `VoiceUpdate` sender. It does not use Songbird's disconnected command buffer. A missing/stale registered sender rejects transmission; disconnected latest intent is bounded and cannot replay a cancelled join. Serenity's awaited `VoiceGatewayManager` hook feeds one ordered actor for own voice state/server updates. Concurrent ordinary/raw event handlers do not own voice correlation. The `join_gateway` wait is outside the actor/Call mutex so incoming state/server events can complete it. Only the dedicated voice worker invokes `Driver.connect`; dropping its Future is not treated as cancellation.

Before an initial guild join, bounded `Http::get_user_voice_state` reconciles existing bot membership. Only documented JSON error10065 means absent; other errors remain unknown/fail closed. A non-null pre-existing session is rejected instead of silently taking it over. REST results carry the gateway epoch, requested room key and captured own-state counter; a newer ordered state invalidates an older REST answer. Initial GuildCreate callbacks cannot overwrite this state. Before voice credentials are handed to a driver, a second current-state check must match the exact requested channel and private voice session, with the same counter fence.

Private room identity comprises destination ID, independent intent generation, guild and requested channel. Credential messages also carry gateway epoch and credential revision. Ordered state is accepted only for the own bot/reserved guild and exact desired channel; unexpected move, removal, mute/suppression or definitive permission denial disarms that room. It never changes user intent to follow Songbird's mutable Call channel. Both server-first and state-first joins are handled, but raw server events are not falsely described as request-correlated: Discord supplies guild/token/endpoint without a channel/nonce. Retired credentials stay in a bounded private deny-set; exhausting its capacity fails the epoch rather than forgetting history.

Leave preserves the guild reservation until both an own null-state received after the leave barrier and actual voice-worker exit are observed. Cancel before any join was issued needs no remote leave. An incomplete issued join retains a disarmed tombstone until owed handshake events are drained and the latest non-null own-state is followed by another leave/null barrier; a late non-null state invalidates an earlier null receipt. Bounded failure leaves visible cleanup-incomplete state instead of reusing an ambiguous guild. Peers continue. Same-card changes stop/leave the old room before joining the new target; unchanged-room selection is a no-op. Removing a card keeps its retirement visible until safe release.

Endpoint/credential refresh first disposes the old voice worker and observes exit, then starts a new reader with a new public output session ID and private worker generation. The still-current request intent is separate from these reader lifetimes. Late old-driver states/meters cannot cross that fence, and unrelated source/output histories do not reset. Permission preflight and bounded per-guild live permission checks are retained.

Shared-gateway fresh Identify/deregistration or exhausted recovery is a terminal epoch boundary: stop that gateway's Discord drivers and require explicit reconnect, preserving sources/playback. Do not blindly replay remembered room wants after potentially missed removal events. Local gateway/driver exit proof remains distinct from a remote leave receipt. Fresh explicit connection reconciles current membership again. Token replacement is blocked by every gateway, voice, startup and retiring lifetime, not a legacy first-room alias.

Public additions are `gateway: GatewaySnapshot { phase, generation, message }` and `serverReservations: ServerReservation[] { serverId, channelId, destinationId, sessionId, phase }`. Gateway phases are disconnected/connecting/connected/recovering/disconnecting/cleanup-incomplete/error; reservation phases are selected/joining/connected/leaving/blocked. Reservations include idle selected targets and retained old guilds during cleanup, so one changing card may own two reservations. Existing card commands are unchanged. All public generation/session values are local application counters; gateway RTT stays scalar telemetry. No token, voice endpoint credential or Discord session ID enters TypeScript, snapshots, settings, logs or Debug output. Private wrappers fully redact even fields that upstream `ConnectionInfo::Debug` prints.

EC-032 reviewed this checkpoint's semantics before production implementation. Required hostile tests cover both handshake orders, every cancel boundary, late old-guild/server/state data, unexpected move/null, disconnected cancelled commands, leave receipt before/after local exit, gateway epoch rollover, per-room fault/permission isolation, and secret canaries across Debug/errors/exports. Real cross-server listener acceptance remains explicitly unmeasured until a coordinated live test is authorized.
