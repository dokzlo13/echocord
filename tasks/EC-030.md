# EC-030 Multiple Discord rooms

Active, native worker a1 on `agent/EC-030-a1` in `.worktrees/EC-030-a1`. Owner now requests planning and implementation of multiple room targets. Dependencies: shared mix and independently controlled output model, plus a reviewed gateway/voice-worker contract before implementation.

Research in EC-020 confirms different-guild calls are feasible. Discord permits multiple gateway sessions, but the current engine's single-guild event/disposal assumptions are not a validated multicall design. Explore one shared gateway owner using pinned Songbird's gateway-only join interface, with independently disposable per-guild voice drivers reading the same native mix. One bot still has one voice channel per guild; simultaneous same-guild rooms require separate identities and a separate credential/UI decision.

Preserve source and playback independence, backend-only credentials and voice connection secrets, bounded readers, per-output generation/gain/mute/telemetry, and observed worker exit as local quiescence. Define how gateway reconnects and stale voice-state/server events map to current room intent, how one guild cancels/leaves without restarting other calls, and how parent death/fatal gateway failure is contained. Do not silently replace the existing room or rejoin after removal/permission rejection.

Acceptance requires meaningful event-order/cancel/cleanup tests and a coordinated live test in separate guilds, including one output failing while another and local playback continue. No token/session data in frontend snapshots or diagnostics. Keep current explicit output UX; no routing matrix, driver or broad redesign is required. This record is a researched proposal, not an implemented capability.

## Authorized implementation scope

Own `crates/core/`, Cargo manifests/lockfile, generated frontend types and core-dependent `src-tauri/src/main.rs` wiring. Coordinator owns BOARD/docs/integration; EC-031 owns handwritten UI. First deliver a source-backed architecture and contract checkpoint for EC-032 independent review; implementation starts after that checkpoint is approved. The owner confirms different servers with the existing bot are sufficient. Implement one room per server under the current bot; multiple bot identities and simultaneous same-server rooms are outside this increment. Preserve the existing four-output total limit and up to three playback devices unless the reviewed contract justifies a change.

Retain the shared native mix and independent playback workers. Define a bounded room/destination count, per-room controls and telemetry, preferences migration/idle restore, per-guild slot reservation and no-op selection behavior. Gateway/session/voice endpoint credentials stay private and redacted; never export them in TypeScript or app snapshots. Network side effects start only from explicit room Connect. Preserve reliable cancel and observed process teardown; do not repeatedly autojoin after user disconnect, removal or permission denial.

Validation: meaningful portable event-order/lifecycle/secret-boundary/persistence tests, Windows compilation and native owned process/protocol tests, combined UI and app gates. A live multi-room listener test requires coordination; no automatic live joins or owner room mutations. Use a separate portable Cargo target and coordinate shared native cache with root. Raw evidence under main ignored .trash/multichannel-epoch/native; never owner/. Provide clean scoped commits and measured limits.
