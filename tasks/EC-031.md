## Initial UI audit and proposed behavior

Verified the clean assigned worktree and manually reopened the requested design/browser skills, source records and current product/design/quality context. This is a capability extension inside the corrected On Air interface, not a new visual direction.

The one-room assumption is concentrated in `RoomPicker`: a global `discordLimit` blocks the entire Discord tab once any Discord card exists, with corresponding fixture/test wording. The lower `DiscordRooms` picker already groups servers/categories and checks other cards per guild, but knows only selected targets, not an old guild still reserved during teardown. App cards, summary/jump chips, per-output controls, session-fenced telemetry and bounded histories already support several destination identities. Bot replacement correctly considers Discord activity only, so playback remains independent.

Primary-source Exa research inspected [Discord voice setup](https://discord.com/developers/docs/topics/voice-connections), its [official source](https://github.com/discord/discord-api-docs/blob/main/developers/topics/voice-connections.mdx) and [Songbird's guild-keyed call manager](https://github.com/serenity-rs/songbird/blob/v0.6.0/src/manager.rs). Voice updates target a guild/channel and channel changes require a fresh voice session; Songbird keys its calls by guild. The UI should therefore explain a configured bot's per-server reservation and never implicitly replace another card. These are protocol/library boundaries, not a claim that duplicate gateway sessions are forbidden by Discord.

Proposed common behavior, pending owner identity scope and EC-030 contract:

- Add opens the existing Discord/Playback picker. Remove the global one-Discord blocker when native capacity permits multiple rooms; choose an unreserved server initially where possible. Search may show reserved rows with a reason and owning card, rather than hiding them.
- For the current bot, another configured room in the same server is a conflict even while idle. Current room is marked Current; a same-ID choice is a no-op. A reservation retained for an old server during change/cleanup remains blocked until observed release. Core metadata/validation stays authoritative, and stale-choice errors remain visible in the sheet.
- Every room retains its own Connect/Cancel/Disconnect, gain/mute, fault, session and history. Add/restore stays idle. Changing one card reconnects that card honestly without leaving peers, resetting their histories or invoking a global Apply. Removal preserves inline confirmation and cleanup-incomplete controls.
- Playback discovery and Play/Stop remain available without bot setup and during room/gateway operations. Source capture stays independent. Existing four-card geometry, fonts, tokens, wide source expansion and measured trends remain unchanged unless the reviewed capacity contract requires a bounded extension.
- Represent a shared bot gateway failure only from explicit native gateway state; do not infer it from one room's permission/capture failure or overwrite actual room phases. Explain it through the bot chip/details and the affected native card messages. Gateway RTT remains gateway data, not voice/listener latency.

Multi-bot/same-server account selection is not frozen before the owner's clarification. Native owner app/voice/audio processes are untouched. Next: review this checkpoint, bind the approved capacity/reservation/gateway contract, then implement and test independent room operations, conflicts/retirement, idle restore, partial/shared failures, stale sessions and the existing five-size keyboard/control gates.
