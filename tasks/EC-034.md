# EC-034 Discord room as a source: feasibility research

Read-only research complete. Worker r1 inspected primary web/Exa sources and pinned dependencies, validated the receive seam and proposed the next proof/design increment. No code, build, credentials, live joins, participant capture, output audio or owner processes were changed. The coordinator verified the principal configuration/packet/decryption findings against pinned source. EC-035 owns the proposed native proof and reviewed production design after the multiple-destination delivery; no receive feature is implemented or accepted yet.

## Owner direction

Allow selecting a Discord server/voice room as an input. Combine the participants' received audio into one source stream and feed the ordinary mix to local playback devices or another Discord room. Individual participant mute may follow later. Treat this as live capture/relay; persistent audio-file recording was not requested. Preserve the active multiple-destination delivery rather than replacing it with this follow-up.

## Initial source-backed feasibility

The pinned Songbird 0.6.0 exposes an optional `receive` feature and `VoiceTick`, which supplies aligned participant packets/decoded samples on a 20 ms cadence. Its default decode configuration uses 48 kHz interleaved stereo i16 PCM, matching the mix rate after native float conversion. Echocord currently builds without `receive`; this is a feasible library seam, not an implemented source. Sources: [pinned receive example](https://github.com/serenity-rs/songbird/blob/3f77b5fa6de3f7354fdd7ef0dfa861518d304cdd/examples/serenity/voice_receive/src/main.rs), [VoiceTick source](https://github.com/serenity-rs/songbird/blob/3f77b5fa6de3f7354fdd7ef0dfa861518d304cdd/src/events/context/data/voice.rs), and the locally inspected pinned manifest/decode code.

Songbird 0.6.0 includes DAVE support, but an open upstream report describes intermittent receive/send failures and participant-specific decryption failures during membership changes. This is a reported risk, not a reproduced Echocord defect. A receive prototype must test members already present, members joining/leaving, silence/resume and encryption transitions with consenting test participants; receiving some frames once does not establish reliable room capture. Sources: [release](https://github.com/serenity-rs/songbird/releases/tag/v0.6.0), [upstream report 310](https://github.com/serenity-rs/songbird/issues/310).

## Design questions and proposed first slice

Research one aggregate room-source card with Capture/Stop, source gain/mute and measured receiving status. Explicit capture joins the selected room; stopping it releases only that room's ownership. Restored network sources should remain idle pending explicit Capture. Do not silently change bot self-deafen/receive behavior for existing output-only rooms. No frontend PCM, persisted audio, transcription or automatic participant messaging is needed.

One bot still has only one room membership per server, regardless of whether Echocord labels it a source or destination. Define reservations across both input and output lifetimes. The simplest candidate increment disallows an output in the source's server, including sending the common mix back into the captured room. Broader bidirectional bridging needs deliberate per-destination exclusion of that room's own audio, rather than a global shared mix that creates feedback. These constraints are proposals for design review, not accepted UI behavior yet.

The native receive worker should mix bounded participant samples and expose a bounded source ring to the audio worker, keeping parent/frontend sample-free. Define participant/SSRC identity and limits, packet loss/concealment, jitter and queue budgets, stale-worker/gateway fencing, absence of incoming speech, server mute/deafen changes, permission/removal behavior, crash/stop and independent peer survival. Keep private voice secrets out of public state and diagnostics. Preserve room identity so a future participant mute can address the correct user through SSRC changes.

Pinned source inspection also shows the default receive playout buffer adds five 20 ms packets (about 100 ms) before the local mix/output path; relay latency must be measured separately from earlier application capture. DAVE receive may discard packets before a user/session decryptor is ready, and this does not always become a public failure event. A connection badge or an empty VoiceTick alone cannot establish successful reception or justify reconnecting a silent room. Sources: [receive configuration](https://github.com/serenity-rs/songbird/blob/3f77b5fa6de3f7354fdd7ef0dfa861518d304cdd/src/config.rs), [receive/decryption path](https://github.com/serenity-rs/songbird/blob/3f77b5fa6de3f7354fdd7ef0dfa861518d304cdd/src/driver/tasks/udp_rx/mod.rs).

The proposed follow-on acceptance starts with feature/build viability and synthetic aggregate conversion/mix/lifecycle tests, then an explicitly coordinated Windows receive-to-playback and cross-server relay experiment. Verify two concurrent speakers, member churn, stop/mute/gain, no audio returning to its source room, bounded latency/resources and preservation of unrelated capture/output workers. Report received PCM, local submission and actual listener receipt as separate measurement boundaries. Do not promise silent rooms can be distinguished from an upstream receive stall without evidence.

## Completed research findings

Enabling `receive` alone is insufficient: Songbird defaults to `DecodeMode::Decrypt`; the receive role must select `DecodeMode::Decode(DecodeConfig::default())`. The current output gateway sends `self_deaf:true`, so receive requires an explicit per-room role while output-only rooms remain deafened. Ordinary receive admission should check VIEW_CHANNEL/CONNECT rather than requiring SPEAK; transmission mute/suppression and reception deafen must be treated separately. Stage channels are outside the recommended first slice. Sources: [pinned configuration](https://github.com/serenity-rs/songbird/blob/3f77b5fa6de3f7354fdd7ef0dfa861518d304cdd/src/config.rs), [Discord permissions](https://docs.discord.com/developers/topics/permissions), [voice-state fields](https://docs.discord.com/developers/resources/voice).

VoiceTick's 20 ms cadence does not guarantee a 20 ms decoded vector: pinned code accommodates 20/30/40/60/120 ms packets. Bound per-speaker carry buffers, reblock samples onto the local audio timeline and sum floats; neither concatenating speakers nor truncating each packet produces the intended stream. Maintain generation-fenced SSRC-to-user mappings from speaking/disconnect events so future mute follows the user through stream changes. Known SSRCs are not a reliable participant count. Sources: [decode sizes](https://github.com/serenity-rs/songbird/blob/3f77b5fa6de3f7354fdd7ef0dfa861518d304cdd/src/driver/tasks/udp_rx/decode_sizes.rs), [receive example](https://github.com/serenity-rs/songbird/blob/3f77b5fa6de3f7354fdd7ef0dfa861518d304cdd/examples/serenity/voice_receive/src/main.rs).

A bounded downstream ring does not establish whole-receiver memory bounds: the library has a per-SSRC playout limit of 64 packet positions, a decoder map without a global participant cap, default 60-second inactivity pruning and an unbounded internal event channel whose handlers are awaited. The proof must establish admission/queue/resource budgets and nonblocking handlers, then review either a small pinned upstream bounds/observability patch or explicit isolated-worker resource containment. Sources: [playout buffer](https://github.com/serenity-rs/songbird/blob/3f77b5fa6de3f7354fdd7ef0dfa861518d304cdd/src/driver/tasks/udp_rx/playout_buffer.rs), [driver channels](https://github.com/serenity-rs/songbird/blob/3f77b5fa6de3f7354fdd7ef0dfa861518d304cdd/src/driver/tasks/mod.rs), [receive task](https://github.com/serenity-rs/songbird/blob/3f77b5fa6de3f7354fdd7ef0dfa861518d304cdd/src/driver/tasks/udp_rx/mod.rs).

Do not adopt the issue reporter's encryption downgrade or silence-based rejoin workaround. Discord documents E2EE-only voice calls from March 2026; missing decoded speech cannot distinguish silence from an upstream receive problem. Same-room duplex also needs a distinct design: removing that room's audio must happen before common-mix clipping, because subtracting it from an already clamped bus cannot reconstruct the other sources. Sources: [Discord voice requirements](https://docs.discord.com/developers/topics/voice-connections), pinned receive code above, and the local `mixing::finish_mix` clamp boundary.
