## Investigation checkpoint

The owner confirmed that rooms in multiple servers generally work. Firefox playback sounding fuzzy while Echocord is present, including a description of no stream or recording, is an uncontrolled listening report. It does not establish whether the Firefox card was stopped or muted, whether a playback output was stopped, or whether Echocord caused the sound. Slightly increased but acceptable delay and about 15 MB for two servers are owner impressions with no timing or memory boundary; they are not automated measurements.

The controller starts the persistent audio worker during activation, even with no inputs. Its 5 ms loop continues writing silent 240-frame quanta to the shared bus and publishes source status about every 100 ms. A stopped or removed card causes its session to retire asynchronously: `CaptureControl::stop` sets the terminal stop state, drops a CPAL recording stream or joins the application-capture thread, and the mixer waits for completion before releasing the slot. A muted card continues to capture and meter by design, while its contribution to the shared mix is zero. No output worker opens a Windows render stream until explicit Play; app capture uses process loopback's included target tree and has no render client. Thus the known idle work can consume some scheduling/CPU resources, but source review alone cannot establish that it alters Firefox's local playback. Pausing it without testing readers would change bus heartbeat, silence and underrun behavior, so this checkpoint makes no speculative scheduling change.

No production runtime path found here changes endpoint defaults, device or session volume, Windows audio category, process/thread priority, or timer resolution. The synthetic capture probe can change its own fixture session volume; it was not run here. The pinned CPAL 0.18.2 WASAPI backend uses shared mode and event callbacks; its real-time thread-priority code is behind the non-default `realtime` feature. `cargo tree --locked --target x86_64-pc-windows-msvc -e features -i cpal` resolved only CPAL's `default` feature for this application. The native process launcher supplies no priority-class flag. Application process loopback requests 48 kHz stereo shared/event capture with automatic format conversion; that format describes the capture stream, not a write to Firefox's render format. Microsoft describes process loopback as target-process-tree capture independent of the endpoint, with silence when the selected tree renders no audio. These observations exclude an intentional route/volume/category change in our code, not an OS, driver, browser or resource interaction.
